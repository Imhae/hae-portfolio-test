Project Overview

Problem & Goals

Full-featured and simple rarely come together.

Problem
  • Peer-to-peer marketplaces need a wide feature set — categories, offers, chat, seller tools, trust and verification — to work at all.
  • That same breadth is what usually makes marketplace apps feel cluttered the moment a new user tries to list or browse.
  • Trust is the real blocker to a first transaction: buyers and sellers who don't know each other need visible reasons to believe the other side is legitimate.
Goals
  • Design a browsing, search, selling, and chat experience that stays simple and intuitive at every step, without cutting marketplace functionality.
  • Give buyers and sellers visible trust signals — identity verification, merchant status — without turning onboarding into friction.
  • Deliver one consistent product across mobile and web, so the experience never has to be relearned when a user switches device.

Design Process

Mobile first, then extended into a second platform.

Structure IA & flows

Mapped the information architecture and core user flows around five tasks: Browse, Search, Sell, Chat, Account.

Design mobile App first

Designed the native mobile app first, establishing the core component set against the tightest viewport.

Extend to web Adapt, don't copy

Extended the same IA to a responsive web app, adapting layout and navigation to a wider viewport rather than stretching the mobile screens.

Refine Iterate

Iterated on layout, components, and navigation across both platforms to keep patterns consistent as new modules were added.

Systematize Design system

Consolidated recurring patterns — cards, badges, buttons, forms — into one shared system reused across every module.

Information Architecture

One structure, two navigation shells.

Both platforms share the same five-task backbone — Browse, Search, Sell, Chat, Account — but each expresses it through the navigation pattern native to its context: a bottom tab bar for the mobile app, a top nav plus a persistent Sell action for the web app.

High-Fidelity Designs

The features that make Swapifly more than a listings grid.

One homepage, every category

Category tabs, a promo carousel, a brand rail (LV, Chanel, Hermès, Rolex, Mercedes-Benz), and a persistent Sell button — the full breadth of the marketplace on one scroll.

AI writes the first draft, seller keeps the pen

Typing a few keywords about an item generates a full, editable description plus optional promotional copy — lowering the effort of the one step most likely to stall a listing.

Sellers see what's working

A per-item report — impressions, clicks, inbox contacts, a 7-day trend — gives sellers a reason to come back to the web app, not just the app.

AI auto-reply, opted in per conversation

Sellers choose which buyers get an AI-assisted auto-reply — a scoped opt-in rather than a blanket chatbot, keeping negotiation in the seller's hands by default.

Merchant trust, broken into checkable steps

A merchant badge expands into three independent checks — physical address, online shop, Business Registration — so trust reads as evidence, not just a checkmark.

Key UX Decisions

Three calls that shaped the product.

01

One system, two native experiences

ConsideredA single responsive layout stretched across breakpoints
ShippedTwo purpose-built experiences sharing one component system

Mobile and web serve different moments — quick browsing/selling on the go versus deeper seller management at a desk. Designing each natively let both moments feel right, without duplicating the visual language.

02

Organized by task, not by menu depth

ConsideredA traditional category-first navigation tree
ShippedA 5-task IA — Browse, Search, Sell, Chat, Account

A marketplace can accumulate categories indefinitely. Anchoring navigation to what a user is trying to do, not what's for sale, kept the structure stable as the catalog grew.

03

Trust as a checklist, not a badge

ConsideredA single "Verified" badge with no further detail
ShippedThree separate, visible checks — address, shop, Business Registration

In a resale market, "verified" alone is easy to distrust. Breaking it into specific, checkable claims gives buyers a reason to believe it, and gives sellers a reason to complete every step.

Challenges

What I'd revisit next.

! Feature breadth kept pulling against simplicity

Verification tiers, a coin economy, AI assistance, and seller analytics all needed a place — the constant tension was keeping the core buy/sell loop from feeling cluttered as each one shipped. Pushing power-user tools like analytics and verification detail into secondary screens, and keeping the primary mobile flow to Browse/Search/Sell/Chat/Account, was the main lever for holding that line.

! Keeping two platforms honestly in sync

Every new pattern had to be validated in both contexts before it shipped. Some mobile-first ideas — like a full-page registration flow — didn't translate cleanly to a wider viewport and needed a genuinely different shape on web (a modal), which meant consistency had to mean "same system," not "same layout."

! Retention content lagged the interaction design

At the time of this review, some of the Coin section's engagement copy — the "Market Insights" task cards in Task Center — was still placeholder text. The interaction pattern for the coin economy was in place before its content strategy was, which is typical, but worth flagging as unfinished rather than presenting it as final.

Reflection

The hardest part of Swapifly wasn't any single screen — it was holding the line on simplicity while the feature list kept growing. Verification, coins, AI assistance, and seller analytics all had a real reason to exist, and the discipline was in deciding what belonged in the primary mobile loop versus what could live one layer deeper. Designing mobile first and then extending — rather than copying — into web forced every pattern to prove itself in two contexts before it shipped, which is slower but caught mismatches early. If I revisited this today, I'd tackle the coin economy's content strategy alongside its interaction design instead of after, and push earlier for usability testing on the verification flow specifically, since trust is the one thing this product can't afford to get wrong.
